# P0 M2 — Handoff, one long-running `midad`, install/doctor, "tell one AI", benchmark harness

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Implementer is Devin CLI from one written brief per task; Claude writes the briefs, runs the suite itself, and sends ONE Opus reviewer over the batch.

**Goal:** A fresh Codex session, given only the word "Continue.", finishes work a Claude Code session started — through the real protocol — and both agents already know a fact the owner told Mida once.

**Architecture:** M1 left capture working but every process opens its own copy of the storage server. That cannot continue: the server keeps its replay-protection list and its instant-deny list in memory (`apps/api/src/auth.ts:67-70`, `deny-overlay.ts:166-169`), so two copies over one data folder overwrite each other's files and the second copy does not know what the first one denied. M2 therefore makes `midad` ONE long-running process that owns the home folder's lock, the storage server, the save loop and the keys; hooks and the `mida` command talk to it over a private local socket. The same server is what M3 hosts remotely (spec A15), so M2 also makes its address configurable.

**Tech Stack:** TypeScript (ES modules, run with `tsx`), Vitest, viem, Hono, Node ≥ 20 built-ins only for the socket (`node:http` over a Unix socket). No new dependencies.

**Spec:** `docs/superpowers/specs/2026-09-20-p0-handoff-design.md` — §5D, §6, §8, §10 and amendments A9, A13, A14, A15. Issue register: `docs/issue-register.md` (the benchmark groups come from it).

**Dates:** M1 finished early (Sep 20). M2 runs Sep 21–26. Every day saved here goes to M3, which A15 made heavier.

### Task 1: one long-running `midad`, and the socket everything else uses

**Files:** Create `daemon.ts`, `daemon-main.ts`, `control.ts`, tests `test/daemon.e2e.test.ts`, `test/control.test.ts`. Modify `runtime.ts`, `hook-main.ts`, `cli.ts`, `index.ts`.

**Interfaces — Produces:**

```ts
// control.ts
export const SOCKET_FILE = "midad.sock"
export interface ControlReply { status: number; body: unknown }
/** Never throws. status 0 = could not reach the daemon within timeoutMs. */
export function callDaemon(home: MidaHome, path: string, body: unknown, options: { timeoutMs: number }): Promise<ControlReply>
/** true once GET /health answers; spawns `spawn()` at most once; gives up after waitMs. */
export function ensureDaemon(home: MidaHome, spawn: () => void, options: { waitMs: number }): Promise<boolean>

// daemon.ts
export interface DaemonDeps { home: MidaHome; network: Network; compile: DrainDeps["compile"]; now(): number; log(entry: object): void }
export function startDaemon(deps: DaemonDeps): Promise<{ close(): Promise<void> }>

// runtime.ts — Network gains one optional field
export interface Network { rpcUrl: string; deployment: Deployment; fund(address: Address): Promise<void>; storageUrl?: string }
```

Routes on the socket (JSON in, JSON out): `GET /health` → `{ ok: true, pid, startedAt, queueDepth }`; `POST /kick` → `{ ok: true }` and schedules a save pass; `POST /handoff` (Task 3); `POST /cli` `{ argv: string[] }` → `{ code, lines }`.

**Rules (each with its first-time and empty case):**

1. The socket lives at `<home>/midad.sock`, created with the folder already at mode `0700`; after `listen`, `chmod 0600`. **First time / stale:** if the file exists and `GET /health` does not answer within 500 ms, it is stale: unlink and listen. If it DOES answer, a daemon is already running: exit 0 without touching anything.
2. The daemon takes `midad.lock` through `Runtime.open` exactly once and keeps it until `close()`. Nothing else in the codebase may call `Runtime.open` on a real home after this task except tests and the daemon. `cli.ts main()` becomes: `ensureDaemon` then `POST /cli`; print the returned lines; exit with the returned code. **Daemon cannot start** (no `network.json`, which means `mida init` never ran): `mida init` is the one command allowed to run in-process, and it starts the daemon at its end.
3. `Network.storageUrl` set → `Runtime.open` does NOT call `startPersistentApi` and uses that URL. Unset → today's behaviour. **Empty string** is treated as unset. The URL must be `https://` or `http://127.0.0.1`/`http://localhost`; anything else throws at open with code `bad-storage-url`. (M3 sets it; M2 only tests it against a second local server.)
4. The save loop replaces the detached drainer: on `/kick`, and every 15 s while the queue is non-empty, run `drainUntilSettled` with the daemon's open runtime. One pass at a time (a flag, not a lock file; `queue/drain.lock` logic stays for the no-daemon fallback). **Empty queue:** no pass, no log line (this closes issue CAP-22, the "pass, all zeros" lines).
5. `hook-main.ts`: after writing the job file, `callDaemon(home, "/kick", {}, { timeoutMs: 150 })`. status 0 → spawn the daemon detached (same env stripping as `drainerEnv`) and return; do not wait. The hook's own time budget stays under 100 ms either way — assert it in a test with a daemon that never answers.
6. `/cli` runs `runCli` with a `print` that collects lines. Owner commands therefore execute inside the daemon. `/cli` refuses any argv whose first word is not in the known command list with code 2 and the usage line — no shell, no eval, arguments are data.
7. Shutdown: `SIGTERM`/`SIGINT` → finish the pass in flight (cap 60 s), close the runtime (which removes the lock), unlink the socket.

**Tests (write first, see each fail):**
- health answers with this pid; a second `startDaemon` on the same home resolves to "already running" and the first keeps serving.
- stale socket file (no listener) is replaced.
- `/kick` with one queued `Stop` job and a stub compiler → the record is readable THROUGH THE SERVER as `codex` (not from our objects).
- hook with an unreachable daemon returns in < 100 ms and calls the spawn stub once; with a reachable daemon calls it zero times.
- `/cli` with `["approve","claude-code"]` → the chain says the capability is valid (`isCapabilityValid`).
- `/cli` with `["; rm -rf ~"]` → code 2, usage line, nothing executed.
- `storageUrl` pointing at a second local server → a save lands in THAT server's data folder and not in `<home>/data`.
- kill -9 the daemon mid-pass, start a new one → lock and socket are taken over, the job is saved once (index `queue/saved-ids.json` prevents the double).

- [ ] Steps: failing test → run, see it fail → smallest code → pass → next rule. Commit: `feat(midad): one long-running service with a private control socket; hooks and the mida command go through it`.

### Task 2: which agent may use which project, signed by the owner (`projects.ts`)

Today any folder holding `.mida/project.json` with a known `projectId` is believed. A cloned repository can carry someone else's `projectId` and would receive that project's context. This task closes that.

**Interfaces — Produces:**

```ts
export interface ProjectApproval { agent: string; projectId: string; root: string /* realpath of the folder holding .mida */; approvedAt: string }
export function approveProject(runtime: Runtime, input: { agent: string; cwd: string }): Promise<ProjectApproval>
export function removeAgentApprovals(runtime: Runtime, agent: string): Promise<number>
/** Reads, verifies the owner's signature, returns the match or a reason. Never throws. */
export function checkProject(runtime: Runtime, input: { agent: string; cwd: string }):
  { ok: true; approval: ProjectApproval } | { ok: false; reason: "not-a-project" | "not-approved" | "list-tampered" | "folder-mismatch" }
```

**Rules:**
1. File `<home>/approved-projects.json` = `{ entries: ProjectApproval[], signature }`. The signature is the owner account's `signMessage` over the canonical JSON of `entries` (sorted by agent, projectId, root). Verified with `verifyMessage` against `runtime.owner` on every read.
2. **First time (no file):** the list is empty; every check returns `not-approved`. **File present, signature wrong or unparseable:** `list-tampered` for everyone; nothing is served and nothing is saved; `mida status` and `doctor` say so. Never "fall back to empty and carry on" silently.
3. `mida approve <agent>` run inside a project folder: if `.mida/project.json` is missing, create it with a random `projectId` (`crypto.randomUUID()`); then the chain approval as today; then `approveProject`. Approving a second project for an already-approved agent skips the chain step and only adds the entry. **Run outside any project (cwd has no marker and is `$HOME` or `/`)**: refuse with `not-a-project`; never create a marker in `$HOME` or `/`.
4. `folder-mismatch`: the marker's `projectId` is on the list for this agent but under a different `root` than `realpath(markerFolder)`. This is the cloned-repo case.
5. `revoke` calls `removeAgentApprovals` and re-signs (spec §5E step 4).
6. The save path (`drain.ts`, where it logs `not-a-project` today) calls `checkProject` and treats `not-approved`, `list-tampered`, `folder-mismatch` as PERMANENT: job removed, code logged.

**Tests:** empty home → `not-approved`; approve then check → ok; hand-edit the file → `list-tampered` and a queued job is removed un-compiled; copy the project folder elsewhere → `folder-mismatch`, compile stub never called; symlinked cwd resolves to the same root → ok; revoke removes only that agent's rows and the file still verifies.

- [ ] Commit: `feat(midad): owner-signed list of which agent may use which project folder`.

### Task 3: the handoff builder and the session-start hook

**Interfaces — Produces:**

```ts
// handoff.ts
export type HandoffResult =
  | { kind: "handoff"; text: string; checkpoints: number; facts: number; readMs: number }
  | { kind: "empty"; text: string; facts: number; readMs: number }        // approved, nothing saved yet
  | { kind: "refused"; text: string; reason: string }                      // one plain line
export function buildHandoff(runtime: Runtime, input: { agent: string; cwd: string; authorNames: Record<string, string> }): Promise<HandoffResult>
```
Socket route `POST /handoff` `{ agent, cwd }` → `HandoffResult`.

**Rules:**
1. Order: `checkProject` → chain validity of the agent's capability (`isCapabilityValid`, the expiry-aware helper from fix A) → `readCheckpoints(runtime, agent, projectId)` → `mergeCheckpoints` → `renderHandoff(merged, { authorNames })` → append owner facts (Task 5; until Task 5 lands, facts = 0).
2. Refusal lines, exact text (they are shown to a model and to a person):
   - not approved / expired: `Mida: <agent> is not approved for this project — run \`mida approve <agent>\` in this folder.`
   - revoked (`CAPABILITY_REVOKED` from the server or the chain): `Mida: <agent>'s access was revoked by the owner. Nothing was shared.`
   - tampered list: `Mida: the approved-projects list failed its signature check. Nothing was shared. Run \`mida doctor\`.`
   - any other failure or a read slower than the time limit: `Mida: no context available right now (<stable code>).`
   Never a partial or older handoff (spec §8).
3. **First time (approved, zero checkpoints, zero facts):** kind `empty`, text `Mida: connected. Nothing has been saved for this project yet.` — so the owner can tell "working, nothing yet" from "broken".
4. The text is wrapped in the existing fence from `render.ts`. `<agent>` is one of the local agent names; the input `agent` is validated with `isSafeName` before it is interpolated anywhere.
5. `inject-main.ts <agent>`: reads stdin (same 1 MB discipline as `hook-main.ts`), takes `cwd` and `hook_event_name`; acts only on `SessionStart`; `ensureDaemon(waitMs 4000)` then `callDaemon("/handoff", …, { timeoutMs: 8000 })`; prints `text` to stdout and exits 0. Daemon unreachable → prints the "no context available right now (daemon-down)" line. It never exits non-zero and never prints to stderr: a failing session-start hook must not block the agent.
6. Log one line per call: agent, kind, reason, counts, `readMs`, total ms. Never the text.

**Tests:** approved + two sessions with `continuesSession` → text leads with the first session's request word for word, and contains both record IDs; zero checkpoints → `empty`; revoked agent → the revoked line AND the server log shows the read was refused by the server (ask the server, not our flag); expired grant (Anvil time travel) → not-approved line; `folder-mismatch` → refusal, zero reads made (spy); slow read (stub 9 s) → the no-context line within 8.5 s; stdin of 2 MB junk → exit 0, one line.

- [ ] Commit: `feat(midad): session-start hook prints the merged context or one plain refusal line`.

### Task 4: `mida install` and `mida doctor`

**Rules — install:**
1. `mida install claude-code` edits `~/.claude/settings.json` (path injectable for tests): adds, for `SessionStart`, `PostToolUse`, `Stop`, `StopFailure`, `PreCompact`, `SessionEnd`, one hook entry whose command is EXACTLY `mida-hook claude-code` (capture events) or `mida-inject claude-code` (`SessionStart`). The command text never contains a path, a version or an environment variable: Codex fingerprints hook text and silently drops a changed one (spike), and the same discipline is kept for Claude Code. `mida-hook`/`mida-inject` are `bin` entries in `apps/midad/package.json`.
2. **First time (file or `hooks` key missing):** create them. **Already installed:** detect by exact command string; change nothing; print `already installed`. **File is not valid JSON:** refuse with `settings-unreadable`, change nothing, never overwrite. Always write via temp file + rename, and keep one `settings.json.mida-backup` from before the first change only.
3. `mida install codex`: same for Codex's hook config (path and format as used by `spike/harness/run.mjs`; read it, do not guess). Events: session start and stop only (Codex has no session-end event; its transcript reader is not in M2). Ends by printing: `Codex must be told to trust these hooks once: open Codex in this folder and approve them. Then run \`mida doctor\`.`
4. `mida uninstall <tool>` removes exactly the entries whose command matches; nothing else.

**Rules — doctor** prints one line per check, `ok` / `PROBLEM: <plain sentence> — <the command that fixes it>`, exit code = number of problems (cap 9):
daemon answers; `network.json` present; owner registered on chain; each agent: approved / expired (with date) / revoked, **read from the chain**; approved-projects signature valid; hook entries present with the exact text; shell has `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` set (warn: stripped for the compiler, names only, never values); queue depth and oldest job age; wallets below the top-up line. `mida doctor --live <tool>` (Claude/Dami only, never Devin, never CI) starts one throwaway headless session and checks the daemon logged a `SessionStart` for it within 60 s — the only way to catch Codex's silent skip.

**Tests:** install into an empty temp file, a file with unrelated hooks (byte-preserved apart from ours), invalid JSON (untouched), twice (idempotent), uninstall restores the original bytes-equivalent JSON; doctor against a home with a tampered list / expired grant (Anvil time travel) / no daemon prints the matching PROBLEM lines and the right exit code.

- [ ] Commit: `feat(midad): install and doctor — installed and working are checked separately`.

### Task 5: "Tell one AI. Every AI you authorize can know." (spec A14)

**Rules:**
1. `requestAccess` stops asking for one hard-coded scope. It asks the grant advisor's policy (`packages/grant-advisor/src/policy.ts:101-110`) for the purpose's full recommended grant: for `project_assistance` that is READ on `profile.skills`, READ+CREATE+SUPERSEDE_OWN on `projects.current`, READ on `preferences.communication`. The owner approves all of it in one `grantBatch`. **Already approved under the old single scope (the M1 homes):** `mida approve` detects the missing scopes on chain and issues only those.
2. `mida remember "<fact>" [--in <namespace>]`: default namespace `preferences.communication`; allowed in M2: `preferences.communication`, `profile.skills`; any other → refuse `namespace-not-enabled` and list the two. The record is written BY THE OWNER with provenance `USER_ASSERTED` (never an agent provenance). **Empty or whitespace-only fact:** refuse `empty-fact`. Over 2,000 characters: refuse `fact-too-long`. The text passes `scrubSecrets`; if the scrubber changes it, refuse `looks-like-a-secret` and store nothing.
3. `readOwnerFacts(runtime, agent)` reads both namespaces as that agent, keeps only records whose ON-CHAIN author is the owner (author id zero per `ContextRegistry.sol:130`) and provenance `USER_ASSERTED`; newest 20; a namespace the agent has no grant for contributes nothing and is not an error.
4. `buildHandoff` appends, inside the fence, a section titled `What you have told Mida about yourself` with one line per fact. **No facts:** the section is omitted entirely, not printed empty. Facts count against the 8,000-character limit AFTER the original request and remaining plan, BEFORE progress entries (progress is what gets trimmed).
5. Third agent: `mida init` also provisions `assistant` with purpose `general_assistance`. Its recommended grant is READ on `preferences.communication` and `profile.skills` only. `mida read --as assistant` prints the facts, then attempts `projects.current` and prints the server's refusal code. Help text calls it "a stand-in for any other assistant you use".

**Tests:** remember → both coding agents' handoff contains the fact, word for word, under the right heading; a fact written by an AGENT into `preferences.communication` (it has no CREATE there — assert the chain refuses; then force one in with an owner-signed `AGENT_INFERRED` record) is NOT shown as something the owner said; `assistant` reads the fact and the server refuses it `projects.current` (assert on the server's response code); `remember ""`, a 2,001-character fact, and `remember "sk-ant-…"`-shaped text are refused and nothing reaches the chain (count records before/after from the server); an M1-style home upgrades with exactly one new `grantBatch`.

- [ ] Commit: `feat(midad): mida remember — a fact told once reaches every authorized agent; least-context third agent`.
