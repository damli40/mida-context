# Plan B — `mida migrate`: move a software-key setup to a new contract, in place, switch last

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Implementer is Devin CLI from one written brief per task (`.devin/briefs/b-task-N.md`); Claude writes the briefs, runs the suite itself, and sends ONE Opus reviewer over the whole batch. **Plan A must be complete (all four tasks, E6 and H6 green) before Task 1 here starts.**

**Goal:** `mida migrate` copies every record a software-key setup owns from its saved contract to the contract this code ships, with provenance unchanged, verifies each record individually, and only then switches the setup. A crash at any point is resumable, and `--undo` restores the old setup.

**Architecture:** The migration builds a **staging home** at `<home>/migrate/target/`: the same owner key, a `network.json` naming the target contract, the setup's own store/sponsor choice, and freshly prepared agent identities. Every existing write path (init steps, approve, record writes) then runs unchanged against the staging home, because every entry point resolves its network through Plan A's `resolveNetwork(home, env)`. The old home is only read. The switch moves the staging identities, network and local store data into the real home as the last step.

**Tech Stack:** TypeScript (ES modules, `tsx`), Vitest, viem, Node built-ins, local Anvil via `localEnvironment()` and `deployLocal()`. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-09-22-deployment-binding-and-migrate-design.md` §2 (decisions 1-8), §5 (5.1-5.4), §8, §10, §11 (spikes S1-S4, all passed). Spike scripts in `spikes/1-4` (untracked) show the proven calls: owner read (`spikes/2-owner-decrypt/run.ts:86-121`), log enumeration (`spikes/4-log-enumeration/spike.ts:267-281`), raw evidence write (`spikes/4-log-enumeration/spike.ts:149-180`), envelope placement (`spikes/3-envelope/run.ts`).

**Consumes from Plan A (unchanged):** `resolveNetwork(home, env, deps)` and `ResolvedNetwork.builtIn` (the migration target), `serviceNetwork`, `refusalCode`, `debugLine`, `POST /shutdown` and `callDaemon`. **No Plan A change is required.** See "Dependencies checked" at the end.

## Global Constraints

- One command per Devin call; never `rm`, `curl`, `env`, `kill`, `claude`, `codex`, `git push/reset/checkout/clean/rebase`; never open `.env`; never `pnpm mida*`; never the testnet. Testnet runs are Claude's or Dami's only, and only on a COPY of a home.
- Never weaken an existing assertion. Exported names and signatures stay; new parameters are optional, and omitting them gives today's behaviour byte-for-byte.
- Logs carry codes, counts and timings only. Never decrypted text, fingerprints, keys, paths or `error.message`.
- **No decrypted text is ever written to disk.** The manifest holds IDs, fingerprints and sizes only.
- Every rule states the first-time case (no `migrate/` folder) and the empty case (a setup with zero records). If a brief leaves one unstated, stop and ask.
- Migration is transport: a migrated record keeps its on-chain provenance label, kind, record type, lineage policy and expiry. The envelope is the only addition. No record is skipped for size; no limit is raised.
- A test that checks what moved reads THE TARGET CONTRACT and decrypts from it; never a value the test itself holds.
- Stage by explicit path. `brand/`, `spikes/`, `docs/evidence/m0-local-anvil.json` are never committed.

### Task 1b: seal once, send the same bytes on every retry (added Sep 22 after Task 1)

**Why (found by Devin in Task 1, confirmed in code):** `sealContextObject` draws a fresh data key
and nonce on every call, so re-sealing the same record gives a different `manifestHash`. The
store accepts a second upload for a contextId only when its `manifestHash` is identical
(apps/api/src/app.ts:285) and otherwise refuses with `COMMITMENT_MISMATCH` (apps/api/src/store.ts:87-88).
A crash after the upload and before the chain write would therefore leave that record
un-writable on re-run. Persisting only the nonce (Task 5 as first written) is not enough.

**Files:** Modify `packages/sdk/src/agent.ts` (split `replay`), `packages/fake-vault/src/fake-vault.ts`
(split the owner write). Tests: extend `packages/sdk/test/replay.test.ts`.

**Interfaces — Produces:**


   epoch), `sendSealed` throws `EPOCH_ROTATION_REQUIRED` unchanged; migration stops loudly (nothing
   rotates epochs mid-migration, because capture is paused and no revoke runs).

```ts
export interface MigrationEnvelope {
  version: 1
  originalChainId: string            // decimal
  originalContract: Address          // old ContextRegistry
  originalRecordId: Hex
  originalCommitment: Hex            // old record's on-chain manifestHash
  originalAuthor: Hex                // old on-chain author id
  originalCreatedAt: string          // ISO-8601

}
export function validateMigrationEnvelope(input: unknown): { ok: true; value: MigrationEnvelope } | { ok: false; errors: string[] }
```

**Rules:**
1. `CheckpointEnvelope` gains `migration?: MigrationEnvelope`. `wrapCheckpoint` and `unwrapCheckpoint` carry it when present and omit the key when absent (ordinary checkpoints stay byte-identical). When present it is validated; an invalid one rejects with `invalid-checkpoint` naming the field.

### Task 4b: a record migrated twice keeps its true origin (added Sep 23, Dami's decision)

**Why (found by Devin in Task 4, confirmed in code):** `attachEnvelope` (migration-envelope.ts:96)
overwrites any `migration` key already in the record, and `measureDestination`
(migrate-manifest.ts:151-160) builds the envelope from the SOURCE record. A record moved A → B → C
would name B as its origin, and a fact's `originalCreatedAt` would become B's on-chain time (the
first migration date): "stated Sep 18" would read "stated Sep 25". **Dami (Sep 23): keep the true
origin.** The envelope shape stays version 1; the middle hop lives in the kept manifest and
`network.json`'s `previous`.

**Files:** Modify `apps/midad/src/migrate-manifest.ts`. Test: extend `apps/midad/test/migrate-manifest.test.ts`.

**Interfaces — Produces:** `ManifestEntry` gains

```ts
origin: {                     // the record's TRUE origin — what its envelope must name
  chainId: string; contract: Address; recordId: Hex; commitment: Hex; author: Hex; createdAt: string
}
```

**Rules:**
1. If the source record's payload carries a VALID envelope (`readEnvelope` returns one), `origin` =
   that envelope's `originalChainId`, `originalContract`, `originalRecordId`, `originalCommitment`,
   `originalAuthor`, `originalCreatedAt`, copied verbatim. Otherwise `origin` = the source record:
   source `chainId`, source `contextRegistry`, `contextId`, `manifestHash`, `authorId`, and
   `createdAtOf(record)`.
2. A source payload whose `migration` key is present but INVALID → `buildManifest` throws
   `invalid-source-envelope` naming the `sourceId`. It is never silently overwritten.
3. The destination envelope is always built from `entry.origin` plus the new `migratedAt`, in
   `measureDestination` and everywhere later (Tasks 5 and 6).
4. `sourceId`, `sourceCommitment` and `createdAt` keep meaning the immediate source record (what
   replay order and per-record verification key on). `fingerprint` still excludes the envelope.

### Task 5: the state machine — staging home, prepare → commit → verify, resumable

**Files:** Create `apps/midad/src/migrate.ts`, `apps/midad/test/migrate-steps.e2e.test.ts`.

**Interfaces — Produces:**

```ts
export type MigrateStep = "preview" | "paused" | "backed-up" | "manifest" | "target-setup" | "agents" | "approvals" | "records" | "verified" | "switched"
export interface MigrateDeps {
  home: MidaHome
  env: Record<string, string | undefined>
  confirm: (text: string) => Promise<boolean>
  print: (line: string) => void
  now: () => Date
  target?: Deployment               // default: resolveNetwork(home, env).builtIn
  stopAfter?: MigrateStep           // tests only: return right after persisting this step (a simulated crash)
}
export async function migrate(deps: MigrateDeps): Promise<{ outcome: "moved" | "refused" | "nothing-to-move"; lines: string[] }>
```

**State:** `<home>/migrate/state.json` (0600): `{ version: 1, step, target, migratedAt, hmacKey (hex), manifest }`. `<home>/migrate/target/` is the staging home: `owner/` copied from the real home (0600 files, 0700 folders); `network.json` = target deployment + the real home's own `rpcUrl`, `storageUrl` and `sponsorUrl` keys verbatim (absent stays absent); `agents/<name>/` prepared identities; `data/` its own local store when the setup uses the local store.
