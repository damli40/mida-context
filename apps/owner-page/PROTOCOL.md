# Terminal ↔ owner-page protocol

How `mida` (the terminal) hands an owner action to the browser page, and how the page hands the
result back. The page side of this contract is implemented in `src/owner/link.ts`; the terminal
side is built in a later round against this document.

The two rules that do the security work:

1. Everything identity-relevant lives inside `req`. `requestHash = sha256(reqBytes)` covers the
   whole request, and the same bytes feed the pairing code — so the code the page shows and the
   code the terminal prints can only match if both sides hold the identical request.
2. The result carries no secret material. The page refuses to serialize any 32-byte value under
   a key named like `prf*`, `seed*`, `secret*`, `private*`, `key` (same sanitiser the device-check
   report uses).

## Inbound: the link the terminal opens

```
https://<page-origin>/<flow>#v=1&req=<base64url JSON>&port=<n>&nonce=<hex16>
```

- `<flow>` is `signup`, `approve`, or `revoke`.
- The URL **fragment** carries everything; a fragment never reaches a server.
- `v` is exactly `1`.
- `nonce` is 16 hex digits (8 bytes), single-use, generated by the terminal and bound to its
  listener's lifetime.
- `port` is the terminal's local listener port, an integer 1024–65535. Optional: when absent the
  page shows the result on screen instead of returning it.
- `req` is base64url-encoded JSON, **at most 8 KB decoded**. Unknown top-level fields are refused,
  as are fields with the wrong type. The page refuses the link before any passkey prompt if any
  of these checks fail.

### `req` fields

| field       | type                        | flows            | meaning |
|-------------|-----------------------------|------------------|---------|
| `chainId`   | integer                     | all              | chain the request is for; the page refuses any value other than the deployment's |
| `owner`     | `0x` + 40 hex               | approve, revoke  | the owner the terminal expects; the page stops early if the passkey derives a different address |
| `request`   | object                      | approve          | the agent's **signed** access request (canonical JSON the agent signed) |
| `manifest`  | object                      | approve, optional | the agent's signed manifest, inlined; when absent the page fetches it from the hosted store by `manifestHash` |
| `agentId`   | `0x` + 64 hex               | revoke           | the agent to revoke |
| `readers`   | `0x` + 64 hex array (≤ 64)  | revoke, optional | agent ids the terminal believes survive the revoke; the page re-checks each on chain before re-wrapping |
| `project`   | `{id: string, label: string}` | all, optional  | the project this request belongs to, for display |
| `entries`   | object array (≤ 256)        | approve, optional | the terminal's current project-list entries; the page re-signs the list with the new grant appended |

Per flow: `signup` must carry **no** `owner` (signup creates the owner); `approve` requires
`owner` + `request`; `revoke` requires `owner` + `agentId`.

### The pairing code

Both sides compute `pairingCode(requestBytes)` = `sha256("mida.pair.v1" ‖ requestBytes)`, then
bytes 0–2 pick three words from the fixed 256-word list and byte 3 gives two digits
(`src/owner/pairing.ts`). The terminal prints it; the page shows, verbatim:

> Only approve if this code matches your terminal:

then the code on its own line, large. The terminal computes it over the exact `req` bytes it
sent; the page over the exact bytes it decoded. Same bytes → same code; a forged or truncated
link can never match.

## Outbound: the return navigation

On success, refusal, or user cancel, the page navigates the **top-level window** to:

```
http://127.0.0.1:<port>/mida-return#nonce=<nonce>&result=<base64url JSON>
```

- The host is **always the literal `127.0.0.1`** — never a name, never taken from the link.
  The port comes from the link but is range-checked (1024–65535) again at return time.
- A navigation is not mixed content and needs no CSP exception: CSP has no shipping `navigate-to`
  directive, and `form-action 'none'` does not apply to `location` assignment.
- **Note for the terminal round:** a URL fragment is not sent in the HTTP request, so the local
  listener cannot see `#nonce=…&result=…` directly. `/mida-return` must serve a tiny static page
  whose script reads `location.hash` and POSTs it back to the same listener (e.g.
  `POST /mida-return` with the raw fragment as the body). That hop stays on 127.0.0.1.

### `result` fields

| field          | type                     | meaning |
|----------------|--------------------------|---------|
| `v`            | `1`                      | result version |
| `status`       | `"success" \| "cancelled" \| "failed"` | what the page did |
| `nonce`        | 16 hex                   | echoed from the link |
| `requestHash`  | `0x` + 64 hex            | `sha256` of the exact `req` bytes the page acted on |
| `owner`        | `0x` + 40 hex or `null`  | the owner address derived from the passkey (null if the ceremony never ran) |
| `transactions` | `0x` + 64 hex array      | chain transaction hashes, in order sent |
| `operations`   | `0x` + 64 hex array      | sponsored user-operation hashes, same order |
| `entry`        | object, optional         | the signed project-list entry (approve) |
| `publicKey`    | `{x, y}` hex, optional   | the passkey's P-256 point (signup) |
| `reason`       | string, optional         | plain-words cause when not `success` |

Nothing else is ever present. In particular: no PRF output, no seed, no private key, no
signature material beyond `entry`.

## What the terminal MUST check before believing the result

The browser's word is never proof. Before acting on a `result` the terminal verifies:

1. **Nonce** — equals the nonce it issued for this listener (single use; expires with it).
2. **requestHash** — equals `sha256` of the `req` bytes the terminal itself built and sent.
3. **Signed entry** — the project-list entry signature verifies against the returned `owner`
   address.
4. **Chain state** — the grant, revocation, or key registration is **read from the chain**. The
   `transactions`/`operations` hashes are hints for where to look, never proof.

A result that fails any check is reported as *"the approval page returned something that does not
match this request"* and nothing is written locally.
